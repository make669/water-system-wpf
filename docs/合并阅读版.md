## 1. 分层架构（依赖只允许向下，事件只允许向上）

```
┌─────────────────────────────────────────────────────────────────────┐
│ L6 表现层  MainWindow / ProcessCanvas / 12 自绘控件 / LogViewer / 对话框 │  ← 把状态渲染成像素
├─────────────────────────────────────────────────────────────────────┤
│ L5 应用层  App(组合根) / MainViewModel / ControlViewModel /          │  ← 状态唯一属主
│            AlarmPanelVM / LogViewerVM / AppStateStore / TagBinding   │    行为编排与封送
├─────────────────────────────────────────────────────────────────────┤
│ L4 业务层  DataPollingService / ControlService / ControlDecision /  │  ← 领域逻辑
│            AlarmService / AlarmCenter / LogService / ValueFormatter  │    不知道 UI 存在
├─────────────────────────────────────────────────────────────────────┤
│ L3 通信层  ModbusClient(三态会话/两阶段读/超时/串行化) /             │  ← 帧协议与字节
│            ModbusFrame / CommStatistics                              │    不知道 Tag 语义
├─────────────────────────────────────────────────────────────────────┤
│ L2 契约层  TagTableLoader(E01~E09) / TagAddress / AlarmConfig       │  ← 唯一事实源
│            (A01~A09) / Utility / AppConstants                        │    fail-fast 拒绝带病启动
├─────────────────────────────────────────────────────────────────────┤
│ L1 模拟层  ModbusServer / ProtocolProcessor / DataStore /           │  ← 与 L3 对等的从站
│            ScenarioEngine / ModbusSlaveSim(劣化注入)                 │    供无硬件全链路运行
└─────────────────────────────────────────────────────────────────────┘
   支撑：持久化（history.db / app_init.json / logs/*.log）+ 配置（TagTable.csv / AlarmConfig.json / Communication.txt）
   展示支撑：HandyControl(D11 基础件壳) + Dark 令牌
```

- **依赖方向**：上层引用下层（L6→L5→L4→L3→L2）；L1 模拟层不依赖任何上层，对 L3 而言它就是"一台 PLC"。
- **事件方向**：下层只发事件/回调（OnDataReceived/OnConnectionChanged/OnQualityChanged/OnStatusChanged/OnAlarmChanged/OnEntry/OnError），上层订阅——下层永远不知道谁在听。
- **双模式不分叉（D5）**：模拟与真机的差异只有一处——连接目标（127.0.0.1:1502 进程内从站 vs PLC IP）；协议栈/服务/界面完全同一路径。禁止"演示专用"特殊逻辑（源仓库 AGENTS.md 产品定调）。

## 3. 四条数据流（系统怎么协同）

```
监视流（每 1s）：
PLC/模拟器 → ModbusClient(分组批量 0x03/0x01) → DataPollingService(解码+Scale)
  → OnDataReceived → MainViewModel(TagValues/徽标/首包同步) → 绑定 → 控件像素

控制流（用户手势，事件写）：
点击旋钮/开关 → ToggleCommand → ControlDecision.Precheck(连接/只读/存在)
  → ConfirmDialog(默认焦点=取消) → ResolveConfirmation → ControlService.WriteCoil(0x05)
  → PostWrite(失败回滚+ERROR 日志) → 下轮轮询回流确认（闭环）

报警流（增量）：
轮询数据 → AlarmService.Evaluate(阈值) → 增量 Raise/Clear
  → AlarmCenter(生命周期+SQLite) → OnAlarmChanged
  → 三处可见：顶栏徽标 / 实时报警卡 / 过程图对象描红（P4）
  → 双击/确认 → Acknowledge(id, Windows 用户名) → 落库

日志流（全链路可追溯）：
任意层 Log(level,msg) → LogService → 文件(全量) + BindingList(INFO+) + OnEntry(全量→F12)
```

**状态体系**：全局 S1~S6（未连接/连接中/已连接/重连中/数据中断/模拟运行）× 各区域显示义务 = 设计书 §1.2 状态矩阵；局部状态机（通信卡两态、泵三态、报警四态）各有映射表。**任何一个像素都应能指出它属于哪条流、哪个状态。**

## 0. 结论速览

1. **这不是"重写一个软件"，而是"UI 换壳 + 接线重造"**。源项目工程层（通信/数据契约/报警/控制/模拟器/测试，约 4500 行）与 UI 层天然分界，工程层经最小适配后整体复用，由 110 项单元测试护航（实测基线 110/110 全绿，见 §8）。
2. **UI 层无法移植，只能重造**：界面重度依赖 Zhaoxi WinForms 控件库（ParaTextBox×24、UPipe×14 等，见 §1.2），该库没有 WPF 版本；用 `WindowsFormsHost` 混排会触发 WPF airspace 限制（WinForms 控件永远浮在 WPF 内容之上、不能参与样式/变换），不可取。因此 UI 以 WPF 自绘控件 + MVVM 重造。**重造分两档（v1.1）**：安全行为语义（确认/回滚/fail-fast/空态诚实）逐条忠实平移；**视觉与布局按《UI人性化设计概要》重设计**——现状 UI 经评审存在 18 项人性化问题（P1~P18：数值未格式化、IP/Port 标签错位、报警时主画面无感、泵故障无灯位、过程图对象无标注等），用户已裁定 WPF 版不再像素级还原。
3. **最大的技术风险不是画界面，而是一条 WinForms 的"天然语义"会消失**：源项目依赖"编程赋值不触发控件事件"（E1 预检结论，FrmMain.cs:629-631）来避免 PLC 数据同步引发控制回写风暴。WPF 数据绑定没有这个天然语义，必须显式设计回写防护（§2.4），并配专项测试。
4. **数据契约零损迁移**：`TagTableLoader.CheckUiBindings` 的签名本来就收**字符串集合**而非控件树（TagTableLoader.cs:254-260），E08/E09 fail-fast 校验在 WPF 侧可以原样复用，只需换一个"绑定名收集器"（§2.5）。
5. **工期估计**：单人 14~20 个工作日（M0~M9，见 §7）。期间 WinForms v1.0 仓库**冻结只读**，作为行为对照基线，不修改一行代码。

### 2.4 回写防护（本项目最大技术风险，专项设计）

**问题本质**：WinForms 中 `sw.Checked = plcValue` 不触发 `CheckedChanged`（E1a 实证，FrmMain.cs:629-631），所以"PLC 数据 → 控件"与"用户点击 → 写 PLC"两条路天然不串。WPF 中如果开关状态走双向绑定，PLC 同步改 VM 属性 → 控件视觉变 → 控件若再发"用户改了"回调 → VM 又写 PLC，形成回写风暴（对现场 = 误发控制指令，**不可挽回**）。

**设计（三层防护，缺一不可）**：

1. **单一状态属主**：开关状态的唯一事实源是 VM 属性；WPF 控件（USwitch/UJogSwitch/URotarySwitch 等价物）视觉一律 `OneWay` 绑定 VM。控件只上报**用户手势**（Command/事件），不反向写状态——从结构上消灭"控件改状态"这条路。
2. **手势与同步分流**：VM 属性 setter 带 `_syncingFromPlc` 抑制标志（对应源 `_handlingToggle`，FrmMain.cs:71,865）。PLC 首包同步（B7）与轮询回写只改状态属性；用户手势走 `ToggleCommand(tagName)` → `ControlDecision.Precheck → 确认 → WriteCoilAsync → PostWrite`。
3. **自翻转语义的等价实现**：源项目中 Jog/Rotary 控件"先自翻转再发事件"（ControlDecision.cs:6-16），USwitch"不自翻转"。WPF 统一为：手势命令先把 VM 状态置为目标值（对应自翻转后的视觉），取消/拒绝/写失败时回写旧值（对应 `RevertNeeded`/`Rollback`）。`ControlDecision` 三阶段纯函数**原样复用**，调用侧把"尚未翻转的当前态"按 kind 映射（Switch: current=旧态；Jog/Rotary: current=翻转后目标态），行为由迁移过来的 ControlDecisionTests + 新增 VM 测试双重覆盖。

**专项验证**（并入 M5）：模拟器正常轮询 60 秒（含 `scenario wave`），TestRunner 在从站侧断言**写功能码（0x05）请求计数 = 0**；用户无操作时零回写，才允许出阶段。

### 2.5 数据契约 E08/E09/W01 在 WPF 的落地

源项目的 UI 绑定核对分两半：控件扫描（WinForms 专属）+ 字符串核对（跨框架）。后者签名（TagTableLoader.cs:254-260）：

```csharp
CheckUiBindings(List<TagAddress> tags,
    IEnumerable<string> controlBindings,   // 控制类绑定的 Tag 名
    IEnumerable<string> displayBindings,   // 显示类绑定的 Tag 名
    List<string> errors, List<string> warnings)
```

WPF 侧做法：所有与 Tag 挂钩的绑定统一走 `TagBinding` 标记扩展（或附加属性 `ui:TagMap.Name="Pump1_F"`），在 XAML 解析/加载完成时把 Tag 名注册进静态注册表（区分控制/显示两类）；启动流程在 `InitializeComponent()` 后调用 `CheckUiBindings` 收集结果——E08（RW 无控制入口）/E09（绑定不存在的标签）继续 fail-fast 拒绝启动，W01 仅警告。**保证"标签表是唯一事实源 + fail-fast"这条产品底线跨框架不变**。绑定注册表实现必须在 M2 交付并配单测（给定一组绑定名 → 错误码逐一断言），防止"注册表漏注册 → 校验静默通过"的假绿——这正是源项目 series3 缺陷（B10）的教训：静默失败比崩溃更危险。

### 6.1 仓库拓扑

| 仓库 | 角色 | 纪律 |
|---|---|---|

### 6.2 分支与提交模型（用户裁定 2026-10-11：**每个任务一条分支，验收达标才并入 master**）

```
master                              ← 只接受任务分支合入；合入前置条件 = 该任务验收全绿
└── feature/T1.1-copy-core          ← 每个 T 任务一条分支（实施细则 §2 任务编号）
└── feature/T1.2-…                  ← 下一任务从最新 master 重新切出
└── …（阶段全部任务合并后打里程碑 tag）
```

- **提交信息**：`{T编号} {一句话}（证据：…）`，中文、含证据（对齐源仓库风格）。
- **合并门槛**：任务的 [自动]/[操作]/[检查] 验收全过 + 证据贴合并描述；未达标不得合并，修不动整支废弃。
- **里程碑 tag**：`v0.0-baseline → v0.1-core → v0.2-shell → v0.3-monitor → v0.4-graphics → v0.5-control → v0.6-alarm → v0.7-trend → v0.8-persist → v1.0-wpf`。
- **回退策略**：问题定位到某任务即回退该分支的合并（revert merge commit）；禁止"先过后面再补"（源验收标准 §0.2 原文）。
- **阶段回归**：里程碑 tag 前重跑此前所有 [自动] 项。

## 3. 关键实现规格（代码级）

### 3.1 App 启动顺序（对应 FrmMain_Load 平移，FrmMain.cs:140-183）

```text
App.OnStartup:
 1. 注册 DispatcherUnhandledException → LogService.Error + 弹窗（不静默退出）
 2. tags = TagTableLoader.Load(BaseDirectory/configFiles/TagTable.csv)
    ├─ errors>0 → FailFastWindow("标签表校验失败…E01~E09 全量") → Shutdown(1)   ← 对应 FrmMain.cs:309-318
 3. cfg = AlarmConfig.Load(…AlarmConfig.json)
    ├─ errors>0 → FailFastWindow("报警配置校验失败 [A01]~[A09]") → Shutdown(1)
 4. alarmCenter = new AlarmCenter(BaseDirectory/data/history.db)
 5. comm 配置读取（Utility.LoadCommunicationConfig）→ 组合根:
    ModbusClient → DataPollingService(SetTags) → ControlService → AlarmService(cfg)
    （与 FrmMain.cs:366-387 同构；订阅关系见 §3.3）
 6. MainWindow = new(); DataContext = mainViewModel; Show()
 7. mainViewModel.OnLoaded(): 恢复持久化 → ResetDisplayValues → 启动看门狗   ← 空态归零先于一切显示
```

```text
ToggleTag(tag):
  if busy: return                                    # _handlingToggle 等价
  tagAddr = tags[tag] ?? → Log ERROR "找不到标签" return
  plan = ControlDecision.Precheck(IsConnected, tagAddr, kind(tag), visualState(tag))
  switch plan.Action:
    RejectNotConnected/RejectReadOnly → revert if needed → 提示 → return
  confirmed = ConfirmDialog(标题"操作确认",
      文案 = ControlDecision.DescribeAction(tag, plan.TargetValue) + " [" + tag + "] 吗？",
      上下文行 = 描述/当前值/目标值/PLC 地址, 默认焦点 = 取消)             # P16
  plan2 = ControlDecision.ResolveConfirmation(confirmed, kind(tag), visualState(tag))
  if plan2.Action == CancelNoop: revert if needed; return
  old = 当前视觉状态; 置视觉 = plan2.TargetValue                       # 自翻转等价（层3）
  try:
    ok = await controlService.WriteCoilAsync(tag, plan2.TargetValue)
    if ControlDecision.PostWrite(ok) == Rollback: 置视觉 = old; Log ERROR 回滚
    else: Log INFO "控制指令已下发 [tag] → ON/OFF"
  catch ex: 置视觉 = old; Log ERROR "控制异常已回滚"
  finally: busy = false
```

## 8. 组件策略（决策 D11：域控件自绘，基础件引库）

"UI 的组件怎么办"——按**工艺语义强弱**分三类处理，不搞一刀切：

| 类 | 组件 | 处置 | 理由 |
|---|---|---|---|
| **A. 自绘控件（12 个）** | 工艺语义 8：PipeLine、PumpGraphic、LevelTank、RingGauge、ParaBox、StatusBadge、AlarmBadgeChip、WaterTrendChart；开关 3：USwitchW、UJogSwitchW、URotarySwitchW；骨架 1：CardChrome | WPF UserControl 自绘，视觉按本文规格 | 工艺语义强（水路因果、报警联动、量程=TagTable），任何库都没有；渲染实证已验证自绘可行（§9） |
| **B. 基础件（引库）** | Card 边框、Button/确认框、TextBox、DataGrid 皮肤、全局深色资源、通知气泡 | **HandyControl**（MIT，NuGet `HandyControl`，.NET 8 实测可用，中文文档/社区活跃） | 无工艺语义，自绘纯费工；渲染实证恰好证明必要性——**原生 DataGrid 默认表头是白底**（PoC 第一轮即出现），逐个样式接管约 1~2 天；HC 提供现成深色皮肤 |
| **C. 混合（原生+样式）** | Canvas 设计稿画布、DataGrid 行着色（LogRowStyler 数据触发） | WPF 原生 + 令牌覆盖 | Canvas/触发器是框架原生能力，引库反而绕路 |

**D11 边界与风险**：
1. HC 只用于"壳"，**不引入其业务控件替代域控件**——避免 Zhaoxi 式绑定（源项目教训：控件库无 WPF 版导致整套 UI 重写）；
2. HC 会重写几乎所有默认控件样式（社区实测反馈），个别需要原生样式时"改回去较复杂"——缓解：T4.1 先做 HC 令牌对齐（把概要 §4.4 令牌映射到 HC 的资源键），T4.9 统一做深色一致性检查；
3. 版本锁定 `HandyControl` **3.5.1**（2026-10-11 实测：NuGet 可还原、HC 命名空间编译通过，迁移方案 §8-9）；MIT 无商用风险；
4. 若坚持"零第三方依赖"（源项目手写 Modbus 的自研哲学），B 类也可自绘——功能无损，工期 +1~2 天；**推荐引库**，把工时留给 A 类域控件和水路联动。

### 1.5.2 为什么深色卡片式与"人性化"不冲突（检索佐证）

ISA-101（高性能 HMI 标准）的通行做法正是：**单一深灰/黑底降低长时值守眩光；正常态设备一律低对比灰调（靠形状与位置传达信息）；饱和色只留给异常**——"gray by default, color for exceptions"。参考图的深色方向与标准同向；要守住的只有一条：**正常态别抢戏，红/黄只给报警**。本项目 P4（报警主画面无感）的修复在深底上反而更醒目。图①的霓虹装饰发光属"展示大屏风"，生产值守界面按上表"克制"行处理。

检索来源：HRSD 自动化标准（ISA-101 深底/灰调/报警色规则）、HMI Library（ISA-101 风格解读）、ThingsBoard SCADA 泵状态监控范例、3D-SCADA 泵卡/仪表组件范例、AVEVA 泵站面板文档、Dribbble/Pinterest SCADA 视觉集。

**Q4 附加约束（验证发现，任一形态都成立）**：
1. **【连接/断开】必须主屏可达**——通信是上位机最高频操作，不得藏进设置页；若选导航形态，顶栏保留快捷连接按钮或通信卡保留操作按钮。
2. "系统设置"页的报警阈值编辑需要 AlarmConfig 的**写回保存**能力，而服务层目前只有 `Load` 无 `Save`（AlarmConfig.cs，迁移方案 §8-2/L2）——阈值编辑 v1 先做**只读展示 + 打开配置文件目录**，写回保存作为后续带测试的增强，不并入 v1.0-wpf 验收线。

## 8. 明确不做（防发明危险功能）

1. **确认弹窗不可跳过**、不可"记住选择"——控制指令的最后一道人关，不做免确认选项；
2. **不自动写值**：任何 UI 改动不得让界面在无人操作时产生写指令（回写防护专项测试继续把关）；
3. **不动服务层语义**：报警生命周期、控制三阶段决策、fail-fast 校验、轮询/退避参数全部原样；
4. **不做多主题/多语言**（沿用 v4 取舍）——深色即唯一主题；
5. **不做组态化编辑器**（拖拽组态列入远期，沿用 v3 取舍）；
6. **装饰发光克制**：深色卡片的霓虹效果仅限悬停/选中反馈，不得用于状态表达（状态只认 §4.4 色板）。
